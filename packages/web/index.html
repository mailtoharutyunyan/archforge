One model, every view

Describe the system once. Context, container, component, deployment and sequence views are projections of that model — so a dependency you declare at component level automatically appears, correctly lifted, on the container diagram. 

system payments "Payment Platform" {
  owner "team-payments"

  container api "Payment API" {
    technology "Java 21 / Spring Boot"
    source "services/payment-api"
  }

  database db "Payments DB" {
    technology "PostgreSQL 16"
  }
}

payments.api -> payments.db "Reads and writes" {
  technology "JDBC"
}

views {
  context   landscape "Landscape" of payments
  container platform  "Containers" of payments
}
  • Stable identifiers Rename a label without breaking a diff. Ids survive refactors.
  • Layout is separate Positions live in their own file. Changing the model never destroys the arrangement you chose; changing the arrangement never looks like a semantic change.
  • Byte-identical renders Same model in, same SVG out — on any machine. That is what makes a diagram reviewable in a pull request.
  • Exports, not lock-in SVG, PNG, self-contained PlantUML, Mermaid, Markdown docs and the raw JSON model.

Architecture rules that fail the build

Write governance as selectors over the graph, not as a wiki page nobody reads. 

rules {
  rule domains "Order must not reach payment internals" {
    severity error
    forbid element(tag:domain-order)
        -> element(tag:internal, tag:domain-payment)
  }

  rule no-cycles { severity error  forbid cycles }

  rule owned {
    severity warning
    require owner on element(kind:container)
  }
}

The part nobody else does: drift

Bind each container to the directory that implements it. Archforge scans the code and tells you where the documented architecture and the real one have parted ways — with file and line evidence, and an honest confidence class rather than a made-up percentage. 

$ arch drift --repo .

ARCHITECTURE DRIFT
16 files scanned · 12 declared · 9 detected

✗ Payment Worker depends on Redis (redis/client), but no declared relation accounts for it
    detector: redis/client · confidence: high
    services/payment-worker/.../IdempotencyStore.java:17  private final StringRedisTemplate redis;
⚠ Payment Worker is declared to depend on Notification Service, but nothing in the code supports it
i  PaymentController has no source binding, so drift cannot be assessed for it

6 finding(s), 1 error(s).

Scanners cover Java/Kotlin, JavaScript/TypeScript, Python, Go, .NET, Ruby, PHP and Rust, plus dependency manifests, Dockerfiles, Compose, Kubernetes and Terraform. Adding a stack is a table entry, not a rewrite. Inferred facts are always labelled as inferred — never silently merged into what a human wrote.

Built for AI agents, safely

Archforge ships an MCP server, so Claude Code, Cursor or any MCP client can read and change your architecture. Agents do not get a CRUD API over your graph — they propose text and are shown the consequences.

1 Agent reads the model and the DSL reference
2 propose — compiles, validates, diffs. Writes nothing.
3 A human reads the structural diff
4 apply confirm=true — only then does anything land

apply refuses a model that does not compile, and refuses one that breaks an error-severity rule unless a human explicitly overrides it.

Command line and CI

# scaffold, then keep it honest in CI
$ arch init
$ arch check --recommended
$ arch render --all --format svg --out docs/diagrams
$ arch drift --repo .
$ arch diff main.arch feature.arch --exit-code
$ arch docs

# exit codes: 0 clean · 1 findings · 2 usage · 3 model does not compile

Zero runtime dependencies. Node 22.6+ runs the TypeScript directly — there is no build step, no bundler and no database. The web editor is static files.
